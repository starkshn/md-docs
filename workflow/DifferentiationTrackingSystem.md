# Differentiation Tracking System

## 목적

Codex는 항상 “이 기능이 왜 일반적인 포트폴리오보다 강한가?”를 분석해야 한다. 기능 구현 전에 차별화 포인트를 정의하고, 구현 후 실제로 증명되었는지 확인한다.

## 기본 질문

각 기능마다 다음 질문에 답한다.

- 일반적인 포트폴리오라면 어떻게 구현하는가?
- 현재 포트폴리오에서는 어떻게 다르게 구현하는가?
- 이 차이가 면접관에게 어떻게 보이는가?
- 실행 화면에서 차이가 보이는가?
- Metrics 또는 Before/After로 증명 가능한가?
- Markdown, PlantUML, Blog Draft, Interview Notes로 설명 가능한가?

## 예시: Object Pooling

일반 포트폴리오:

```text
Object Pool 구현
Pool Manager 하나 생성
```

현재 포트폴리오:

```text
Object Pool Module
Feature Toggle 가능
Before/After 비교 가능
Metrics 제공
Debug UI 제공
문서화 완료
블로그 작성 완료
Interview Notes 작성 완료
```

## 예시: Skill System

일반 포트폴리오:

```text
Skill System 구현
스킬 몇 개 실행
```

현재 포트폴리오:

```text
모듈형 Skill Architecture
Skill Editor
Validation Framework
Feature Toggle
Metrics
Before/After Comparison
Blog Series
PlantUML
Interview Notes
```

## 기능별 차별화 포인트 기록 템플릿

```markdown
# Differentiation - Feature Name

## 일반적인 구현

## 현재 포트폴리오 구현

## 차별화 포인트

## Before / After 증명 방식

## Metrics 증명 방식

## 문서화 포인트

## 블로그 포인트

## 면접 설명 포인트

## 개선 여지
```

## Codex의 역할

Codex는 단순 코드 생성기가 아니다. 항상 아래 역할을 수행해야 한다.

1. Architect
2. Reviewer
3. Documentation Writer
4. UML Designer
5. Blog Assistant
6. Interview Coach

## 최종 목표

최종 목표는 “Unity 포트폴리오 완성”이 아니다.

최종 목표는 “기술적으로 설명 가능한 개발 과정 자체를 포트폴리오화”하는 것이다.

따라서 모든 기능은 반드시 아래 산출물을 남겨야 한다.

- Source Code
- Git Commit
- Markdown
- PlantUML
- Notion Journal
- Blog Draft
- Interview Notes

Codex는 매 작업마다 다음을 정리해야 한다.

- 이번 작업에서 배운 개념
- 이번 작업의 차별화 포인트
- 블로그로 작성 가능한 내용
- 면접에서 설명할 수 있는 내용
